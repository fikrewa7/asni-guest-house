The Problem

Small guest houses run on paper and phone calls

Manual hotel management creates real operational pain in the Ethiopian hospitality sector.

Paper Registers
Room bookings, guest IDs, and check-in dates are written by hand. A single water spill or lost notebook means lost revenue and legal traceability.
No Online Presence
Walk-ins only. Travellers researching Jimma on Google have no way to see room availability, prices, or menu before arriving.
No Staff Roles
Everyone can see everything. There is no separation between owner, receptionist, and guest — a compliance and privacy problem.
The Opportunity
Jimma sits on a growing tourism corridor (Aba Jifar Palace, coffee farms, university visitors). A small, focused web app can triple booking visibility at near-zero infrastructure cost.
Project Objectives

What this app is built to solve

Digitize the Booking Flow
Replace paper registers with a searchable, filterable bookings table backed by a real database.
Role-Based Access
Distinct experiences for Admin, Receptionist, and Guest — enforced on the frontend and validated on the backend.
Full CRUD on All Entities
Rooms, Users, Bookings, Menu Items, Orders, Tables, and Banners — create, read, update, delete.
Zero-Cost Hosting
Deployable on free tiers of Vercel (frontend) and Cloudflare (edge API + D1 database).
Framework-Free Frontend
Build a full SPA-like experience using only HTML, CSS custom properties, and vanilla JavaScript — no React, no Vue.
Production-Ready UX
Toast notifications, glassmorphism, responsive layout, live charts, and keyboard-accessible modals.

System Architecture

Three-tier, edge-first architecture

Client Browser
index.html · style.css · app.js
Cloudflare Worker
POST /api/query · JSON
Cloudflare D1
SQLite at the edge
Request Lifecycle
  • User clicks a button in the SPA
  • JS calls apiQuery(sql, params)
  • fetch() POSTs JSON to the Worker URL
  • Worker prepares & binds the SQL statement
  • D1 executes and returns rows
  • JS re-renders only the affected views
Why This Architecture?
  • No server to manage — Cloudflare runs it
  • Global low latency — data served near the user
  • Parameterized SQL — prevents SQL injection
  • Offline fallback — app caches data in localStorage if the API is down
  • Free tier friendly — 100k requests/day on Workers

Backend API

One endpoint, all the power

A single POST /api/query endpoint handles every CRUD operation with parameterized SQL.

// Cloudflare Worker — request handler
export default {
  async fetch(request, env) {
    // 1. CORS preflight
    if (request.method === "OPTIONS") { ... }

    // 2. Health check
    if (url.pathname === "/api/health") { ... }

    // 3. SQL execution endpoint
    const { sql, params } = await request.json();
    const stmt = env.DB.prepare(sql);
    const boundStmt = params.length
      ? stmt.bind(...params) : stmt;

    const result = sql.toUpperCase().startsWith("SELECT")
      ? await boundStmt.all()
      : await boundStmt.run();

    return Response.json({
      success: true,
      results: result.results
    });
  }
};
Security: Parameterized SQL
Instead of concatenating user input into SQL strings, we use bound parameters. db.prepare("... WHERE id = ?").bind(id) means D1 sends the SQL template and values separately — SQL injection is impossible by design.
CORS Handled
Proper Access-Control-Allow-Origin headers let the Vercel frontend call the Worker from a different domain.
Edge Execution
The Worker runs in Cloudflare's V8 isolates — cold starts under 5ms, no container to boot, no region to choose. It scales to zero when idle.

Frontend · Design Philosophy

Five principles that shaped every screen

Clarity
Information is hierarchically organised. KPI cards first, then charts, then tables. No competing focal points.
Feedback
Every action produces a visible response — toasts, button state changes, or animated re-renders.
Role Awareness
The UI visibly changes colour and layout based on the currently active role.
Mobile-First
Every layout starts from the smallest viewport and expands. No horizontal page scroll.
Performance
Zero frameworks, zero bundlers. Three files, cached forever, loaded in under 200ms.
The core belief
A well-designed admin UI is not decoration — it is operational efficiency. A receptionist who can check in a guest in 12 seconds instead of 90 saves the guest house real money.
Frontend · Layout Architecture

A fixed shell with a single scroll region

The most common CSS bug in admin dashboards is page-level overflow. This layout prevents it entirely.

App Shell
The <body> is a flex column at 100dvh (dynamic viewport height) — the header is fixed, everything else stretches to fill.
Body Row
A flex row containing sidebar (fixed 15rem) and main (flex: 1). min-height: 0 on both is critical — it is the secret that stops flexbox children from overflowing.
Only Main Scrolls
overflow-y: auto lives on .app-main only. The sidebar has its own scroll region. The page itself never scrolls — this eliminates the classic double-scrollbar bug. 
/* style.css — the fixed shell */
.app-shell {
  display: flex;
  flex-direction: column;
  height: 100dvh;
  overflow: hidden;      /* kill page scroll */
}

.app-body {
  flex: 1;
  display: flex;
  min-height: 0;      /* ← the critical fix */
  overflow: hidden;
}

.app-sidebar {
  width: 15rem;
  flex-shrink: 0;
  overflow-y: auto;      /* own scroll */
}

.app-main {
  flex: 1;
  min-width: 0;

Frontend · State Management

Single source of truth, one-way data flow

No Redux, no Context — just a plain object and a disciplined rendering pipeline.

// app.js — the entire client state
let db = {
  rooms: [], users: [], bookings: [],
  restaurant_tables: [], menu_items: [],
  orders: [], ad_banners: []
};

let currentRole = 'Admin';
let activeCart  = [];     // transient UI state

/* Rendering pipeline */
function renderAll() {
  renderDashboard();
  renderRooms();
  renderUsers();
  renderBookings();
  renderRestaurant();
  renderTables();
  renderReports();
  renderBanners();
  renderSchema();
}

/* After every mutation → reload + re-render */
async function handleRoomSubmit(e) {
  e.preventDefault();
  await dbInsert('rooms', payload);
  await reload();        // pulls from D1
  renderAll();          // repaints views
}
The Flow
  • User clicks a button
  • Handler builds a payload
  • dbInsert/dbUpdate/dbDelete calls the API
  • reload() fetches fresh data from D1
  • renderAll() repaints every view
  • User sees the change with a success toast
Offline Fallback
If the API is unreachable, the same state object is populated from localStorage. Every mutation also writes back to localStorage. The app still works offline.
Why this works
Predictable, easy to debug — the state is always visible from DevTools, and every render is idempotent (safe to call any number of times).
Frontend · Interactive Components

Building a component library without a framework

Modals
One shared .modal class drives 9 different forms. Open with a dynamic title, close with click-outside, ESC, or an X button. Focus is trapped while open.
Cart
Adding the same item increments quantity instead of duplicating. The cart persists through modal reopens. Submission serializes to JSON for the items_json column.
Toast System
Every CRUD action produces a bottom-right toast. Success = green, error = red. Auto-dismiss in 3.2s with a smooth fade-out.
Live Charts
Chart.js draws revenue trends and room categories on <canvas>. Instances are destroyed before re-creating to prevent memory leaks.
Data Tables
Responsive tables hide non-critical columns below md and lg. Every row has icon-only Edit/Delete buttons for a compact footprint.
Receipts
A dedicated print stylesheet transforms the modal into a clean, black-on-white invoice when Ctrl+P is pressed.
CSV Export
Financial reports are computed live from bookings + orders, then serialized to CSV and downloaded via a Blob URL — no server round-trip.
Accessibility
Tab order follows visual order. Buttons use real <button> tags, not divs. ESC closes any modal. Focus rings are preserved.
The pattern
Every "component" is a self-contained function that builds DOM once and then only replaces innerHTML on re-render. Combined with event delegation where possible, this keeps the DOM updates fast enough to feel instant.
Frontend · Responsive Design

Mobile-first, tested to 320px

Every layout decision starts small and expands. Breakpoints at 480, 640, 768, and 1024px.

Mobile (≤ 480px)
  • Sidebar becomes an overlay drawer
  • KPI cards stack 2-per-row
  • Tables hide low-priority columns
  • Modals become full-height sheets
  • Charts shrink to 13rem height
Tablet (≤ 768px)
  • Sidebar toggles via hamburger
  • Grid collapses to 2 columns
  • Numeric tables stay compact
  • Modals cap at 92vh with scroll
  • Tap targets ≥ 44px
Desktop (≥ 1024px)
  • Full 15rem fixed sidebar
  • 4-column KPI grid
  • Wide 3-column dashboard
  • Hover states on all rows
  • Charts at 16rem height
The `min-width: 0` trick
The single most important CSS rule in the entire layout. Without it, flex children refuse to shrink below their content size — a 900px table inside a 500px column pushes the whole page wide. Adding min-width: 0 to the flex parent allows the table to scroll within its own box instead of exploding the layout.
Fluid typography
Headings use clamp(1.7rem, 3vw, 2.6rem) so they scale smoothly with viewport width. No awkward jumps between breakpoints — text feels native on any device.

Optimizations Applied
  • No build step. HTML/CSS/JS ship exactly as written — Vercel serves them straight from its CDN
  • CDN-hosted libraries. Tailwind, Chart.js, and Font Awesome come from jsDelivr / cdnjs — cached across the web
  • Chart instance reuse. .destroy() before recreating prevents memory leaks on repeated renders
  • Event delegation where lists are long — one listener handles hundreds of rows
  • Only innerHTML swaps on re-render — no node cloning, no virtual DOM overhead
  • LocalStorage cache — zero-latency reads while the network fetch happens in parallel
Trade-offs considered
  • No tree-shaking — but total JS is under 60KB before gzip, so it doesn't matter
  • Full re-render on mutation — acceptable because tables have ≤ 100 rows each
  • Inline SVG icons via Font Awesome — heavier than a custom icon set, but consistent and free
  • Tailwind via CDN — no purge step, so a few unused classes ship; cost is ~15KB gzipped

Theming & Localisation

Two cross-cutting features that make the app usable by every guest, in every condition — day or night, in English or Amharic.

Frontend · Theming

One attribute, two complete themes

A dark-first design with a fully-crafted light variant — togglable in one click, persisted across sessions.

The mechanism
Every themeable value lives in a CSS custom property. The theme is switched by setting data-theme="light" (or "dark") on <html> — one attribute flip.
Semantic variables
No component references raw colours. They only reference tokens like --bg, --panel, --border, --text, --muted. That means one variable block swaps the entire visual identity of the app.
Persistence & sync
Choice saved to localStorage under asni_theme_v1. On every boot, applyTheme() reads it back and re-applies before paint. Charts redraw with appropriate grid/tick colours for the active theme. 
/* Dark — the default */
:root {
  --bg:         #05080f;
  --panel:      rgba(30,41,59,0.7);
  --border:     rgba(148,163,184,0.14);
  --text:       #e2e8f0;
  --muted:      #94a3b8;
  --input-bg:   #1e293b;
}

/* Light — only overrides what changes */
[data-theme="light"] {
  --bg:         #f1f5f9;
  --panel:      rgba(255,255,255,0.85);
  --border:     rgba(15,23,42,0.10);
  --text:       #334155;
  --muted:      #64748b;
  --input-bg:   #f8fafc;
}

/* Toggle in JS */
function applyTheme(theme) {
  document.documentElement.setAttribute('data-theme', theme);
  localStorage.setItem('asni_theme_v1', theme);
  renderCharts();  // redraw with light-friendly colours
}
Why this matters for UX
Reception staff work day and night. A bright light theme is comfortable for daytime check-ins; a dark theme reduces eye strain during night shifts. Providing both — and remembering the choice — is a small feature that has a real impact on the people using the app 8 hours a day.
Frontend · Localisation

Full Amharic (አማርኛ) translation, zero dependencies

A hand-written i18n system in ~80 lines of JavaScript — no i18next, no react-intl, no build step.

Dictionary structure
A single JS object T with two keys: T.en and T.am. Each holds ~160 keys covering headers, tables, forms, toasts, modals, receipts, and enums.
Automatic application
Every static label carries a data-i18n="key" attribute. applyLang() walks the DOM once and swaps textContent for each matching key. Titles use data-i18n-title.
Safe fallback
t(key) → T[lang][key] || T.en[key] || key. If a translation is ever missing, the UI silently falls back to English — it never shows a raw key like "btn_add_room".
Font swap on demand
When lang="am", the body gets a .lang-am class that switches the font stack to Noto Sans Ethiopic — the correct typeface for the Ge'ez script. 
/* Dictionary */
const T = {
  en: { nav_rooms: 'Rooms',   status_Available: 'Available', ... },
  am: { nav_rooms: 'ክፍሎች',  status_Available: 'ነፃ', ... }
};

/* Lookup with fallback */
function t(key) {
  return (T[currentLang] && T[currentLang][key])
      ||  T.en[key] || key;
}

/* One-call application to the whole DOM */
function applyLang(lang) {
  currentLang = lang;
  localStorage.setItem('asni_lang_v1', lang);
  document.documentElement.setAttribute('lang', lang);
  document.body.classList.toggle('lang-am', lang === 'am');

  document.querySelectorAll('[data-i18n]').forEach(el => {
    el.textContent = t(el.dataset.i18n);
  });

  renderAll();  // repaint dynamic content
}
The critical DB decision
Database values stay English-only. When a room's status is 'Available' in SQLite, it stays 'Available' — because the CHECK(status IN ('Available','Occupied',…)) constraint requires exact English strings. Translation happens at render time: t('status_' + r.status). This means the schema never needs to change and translations can evolve independently.
What gets translated
  • All navigation, page titles, and subtitles
  • Table headers, form labels, and button text
  • Modal titles and toast notifications
  • Status pills, room types, zones, categories, roles
  • Receipt template and print labels
  • Chart legends and month names

Frontend · Architecture Trade-offs

Why hand-written i18n beats a library here

A deliberate engineering decision — not a shortcut — for a project at this scale.

~80 lines total
The entire i18n layer — dictionary, lookup, DOM application, language switch, font swap, and chart refresh — fits in a single function plus a constant object. Comparable coverage via i18next would require ~35KB of dependencies, a plugin for the browser, and a build-step configuration.
No XSS surface
Because translations live in a JS object and are set via textContent (never innerHTML), malicious translation strings cannot inject markup. Library-based solutions often require deliberate configuration to guarantee the same property.
Total control over fallbacks
Missing key → English fallback → key string. That three-tier fallback is written explicitly, so a translator can add a language in 30 minutes without learning a config format.
Separation of concerns
The database stores canonical English values that satisfy SQL CHECK constraints. The UI is the only layer that translates. This means the schema is portable to any language without migrations, and the same D1 database could serve a French or Oromo frontend tomorrow — just add T.fr or T.om.
Zero runtime overhead
No network request for locale bundles. Both dictionaries ship inside the same app.js file (~60KB total). Language switching is instantaneous — a synchronous DOM walk, no async fetch, no loading spinner.
Learning value
Writing i18n by hand forces you to understand the real problem: dynamic text is a first-class concern. You learn to design for translation from day one instead of retrofitting it. That knowledge transfers to any framework or library you use later.
Summary
Theming and localisation are not just features — they are architecture decisions that prove the codebase is well-factored. If adding a new theme or a new language were painful, that would be a signal the code was not properly separated. Here, both took less than a day each because the design used semantic tokens and a single source of truth for user-facing text.

Security & Data Integrity

Defense in depth

SQL Injection Prevention
Every query uses parameterized statements. The SQL template and the data travel separately through the Worker to D1 — user input can never become executable SQL.
Output Escaping
Every string inserted into the DOM is passed through escapeHtml() before interpolation. This blocks stored XSS even if a malicious string reaches the database.
CHECK Constraints
Roles, room types, statuses, zones, and categories are all validated at the SQLite layer. Bad data is rejected at the source — no defensive parsing needed in the UI.
Referential Integrity
Bookings reference rooms.id via foreign key with ON DELETE CASCADE. Deleting a room safely cleans up its bookings.
Frontend-side role enforcement
Roles hide UI elements and disable buttons. This is presentation-level security — it improves UX but is not a substitute for real authentication. For a production system the next step would be Cloudflare Access or a JWT-based auth layer added to the Worker.

Challenges & Solutions

What was hard, and how it was solved

Challenge 1 — Page overflow
Symptom: On narrow screens the entire page scrolled horizontally whenever a wide table was present.

Root cause: Flexbox children default to min-width: auto — they refuse to shrink below their content's intrinsic width.

Fix: min-width: 0 on every flex parent + overflow-x: auto on a .table-wrap ancestor. Tables now scroll internally; the page never does.
Challenge 2 — Chart memory leaks
Symptom: After switching between dashboard and other tabs 20+ times, the page became sluggish.

Root cause: Chart.js keeps a reference to every canvas until explicitly destroyed.

Fix: Track each instance in a module-level variable and call .destroy() before every re-render.
Challenge 3 — Role switching breaks the UI
Symptom: Switching from Admin to Guest while on the SQL Console tab left the user stranded on a hidden page.

Fix: After applying role filters, if the currently active tab is now hidden, programmatically click the Dashboard tab. Also disabled all .can-edit buttons for guests.
Challenge 4 — Offline resilience
Symptom: If the Cloudflare Worker was briefly unreachable the whole app showed blank tables.

Fix: On boot, try D1 first; on failure, transparently load the last cached state from localStorage. A toast informs the user that they're offline — but everything still works.
Challenge 5 — Theming without duplication
Symptom: Every styled component would need two full CSS rule blocks — one dark, one light — leading to 3,000+ lines of duplicated CSS.

Fix: Introduced CSS custom properties for every colour token. Light theme became a ~20-line override block instead of a full stylesheet.
Challenge 6 — Localising DB-driven content
Symptom: Room statuses and categories come from the database as English strings locked by CHECK constraints. Translating them at the source would require migrating the schema.

Fix: Kept the canonical values English-only, and built a dedicated translation layer (t('status_' + value)) that maps DB values to display strings for every locale.
